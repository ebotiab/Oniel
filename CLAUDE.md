# Oniel

Web en español para descubrir cómo está conectada la red ferroviaria española. Lo principal es un mapa interactivo en el que se recorre cada línea, con su esquema vertical al lado, y se seleccionan estaciones y tramos; como herramienta secundaria, se simula el cierre hipotético de un tramo en una franja horaria. Está pensada para quien no sabe de ferrocarril y quiere consultar y entender la red de forma clara, intuitiva y atractiva: todo se diseña para esa persona. A quien trabaja en el sector puede serle útil, pero no se diseña nada pensando en él. Hoy carga quince líneas y los dos baipases de la de Barcelona (alta velocidad Madrid – Sevilla, convencional Madrid – Alcázar de San Juan – Córdoba, convencional Manzanares – Ciudad Real, que une las otras dos, el ramal convencional Espelúy – Jaén, la convencional Linares-Baeza – Moreda – Granada, la convencional Alcázar de San Juan – Albacete, las de alta velocidad Córdoba – Málaga, Antequera – Granada, Madrid – Zaragoza – Barcelona, Madrid – Cuenca – Valencia y Albacete – Alicante y las cuatro de Extremadura: convencional Madrid – Talavera de la Reina – Plasencia, alta velocidad Plasencia – Cáceres – Badajoz, convencional Aljucén – Mérida y convencional Monfragüe – Cañaveral – Cáceres) con los horarios de Renfe y de Ouigo, y está publicada en https://oniel.vercel.app con la API en Render.

Este fichero orienta a una sesión que llega sin contexto. No repite el README ni los documentos de `docs/`: los enlaza.

## Todo en español

Interfaz, documentación, comentarios del código, nombres y mensajes de las pruebas, mensajes de commit y descripciones de PR van en español. Los identificadores del código (`segments`, `stop_mappings`, `fetch_alternatives`) siguen en inglés, como están. Las palabras de la interfaz son las del visitante: «tramo», «estación», «cierre», no jerga; cuando un término técnico es inevitable (PAET, bifurcación), se explica.

## Dónde está cada cosa

- `README.md`: arrancar desde cero, comandos de datos, pruebas y comprobaciones.
- `backend/`: API FastAPI, CLI `oniel-data` (Typer), reglas de simulación en `oniel.sim`, grafo de rutas en `oniel.routing`, análisis en `oniel.analysis`, importadores y pruebas pytest. Los módulos se describen en `backend/README.md`.
- `backend/data/raw/`: ficheros originales, con la fecha en el nombre; no se editan. `backend/data/curated/`: una especificación JSON por línea, `sources.json` (el registro de todas las fuentes) y `anotaciones.json` (las anotaciones de red; hoy, las interrupciones del servicio, que se revisan a mano como dice `docs/datos.md`).
- `frontend/`: visor React + TypeScript + Vite + MapLibre, con las pruebas Playwright en `frontend/e2e/`. `frontend/public/data/` es la instantánea estática que exporta el importador; el visor arranca siempre con ella.
- [docs/diseno.md](docs/diseno.md): las decisiones de diseño (tokens, tipografía, composición, encuadre, principios).
- [docs/datos.md](docs/datos.md): fuentes y licencias, cómo se verificó cada línea, modelo de datos y el procedimiento «Añadir otra línea».
- [docs/simulacion.md](docs/simulacion.md): método de la simulación, recorrido alternativo, caso comprobado a mano y límites conocidos.
- [docs/despliegue.md](docs/despliegue.md): Vercel (visor), Render (API y PostgreSQL), Logfire y base de datos local.
- [docs/hoja-de-ruta.md](docs/hoja-de-ruta.md): el orden de las tareas pendientes y los principios de arquitectura; el brief de cada tarea está en su incidencia de GitHub (`gh issue view <número>`). Cada sesión nueva coge la siguiente cuyas dependencias estén cerradas.
- `.github/workflows/ci.yml`: lo que comprueba el CI en cada PR y en `main`; `.github/scripts/que-cambia.sh` decide qué mitad se salta según las rutas que cambia la PR. `.github/workflows/recordatorio-interrupciones.yml`: comprueba cada día si toca revisar las interrupciones y abre una incidencia. `.github/workflows/gtfs.yml`: descarga cada lunes el GTFS de Renfe y, si el horario cambió, abre una PR con el fichero nuevo y la instantánea (`docs/datos.md`, «Refresco de los horarios»); no fusiona nada. `.vscode/`: intérprete `backend/.venv`, Ruff como formateador y pytest desde `backend/`.

## Arrancar y comprobar

Los comandos están en el README y no se repiten aquí: «Arrancar desde cero» (Docker para PostgreSQL, uv y Node 20), «Pruebas» y «Comprobaciones». Para fusionar una PR tiene que estar todo esto en verde, y quien lo pasa entero es el CI:

- Backend: `ruff format --check`, `ruff check`, `mypy` (estricto), `pyright` (modo `standard`, el mismo que Pylance), `pytest` con `ONIEL_TEST_DATABASE_URL` apuntando a una base `oniel_test`, y `oniel-data validate`.
- Frontend: `npm run typecheck`, `npm run lint`, `npm run build` (que al final comprueba las hojas de estilo compiladas) y Playwright con `ONIEL_E2E_STATIC=1` (la instantánea estática, sin servidor), que en el CI va repartida en cuatro fragmentos a la vez.

En local, antes de abrir la PR, la sesión pasa lo rápido y lo que ha tocado, no todo otra vez:

- Las comprobaciones rápidas de la mitad tocada, siempre: formato, lint y tipos en el backend; tipos, lint y compilación en el visor. Son segundos.
- Las pruebas de lo tocado. En el backend, `pytest` (un minuto) y `oniel-data validate` si cambian datos. En el visor, los ficheros de Playwright del comportamiento tocado y los nuevos, con `ONIEL_E2E_STATIC=1` (por ejemplo `npx playwright test e2e/fichas.spec.ts`). La batería completa de Playwright no se pasa en local: la pasa el CI, en menos tiempo y sin ocupar el equipo. Tampoco cuando la tarea toca datos o regenera la instantánea; para eso están los ficheros de lo tocado.
- Lo que el CI no cubre: las pruebas que necesitan la API (`alternativas`, `arranque`, `interrupciones`, `rutas` y `simulacion`, las que llevan `test.skip(estatico, …)`). Cuando se toca la simulación o la API se pasan esos ficheros con la API local arrancada y sin `ONIEL_E2E_STATIC`, no la batería entera.
- En local Playwright usa dos procesos (`frontend/playwright.config.ts`), porque varias sesiones prueban a la vez en el mismo equipo y con más se frenan entre todas. No se sube ese tope desde una sesión; `ONIEL_E2E_WORKERS` queda para quien prueba a solas.

Tras fusionar `main` en la rama no se repite en local lo que el CI va a volver a pasar: se resuelven los conflictos, se pasan las comprobaciones rápidas, se regenera la instantánea si toca y se sube.

El CI mira qué rutas cambia cada PR y salta la mitad a la que el cambio no puede afectar: una PR de solo documentación no lanza pruebas, una que solo toca el visor no lanza el backend, y una que solo toca código del backend no lanza Playwright. `Backend` y `Frontend` quedan en verde igualmente. Las reglas están en `.github/scripts/que-cambia.sh`; quien añada una prueba que lea un fichero de la otra mitad o de `docs/` tiene que añadirlo allí. En `main` corre siempre todo.

El editor no debe mostrar avisos que esas órdenes no den: `.vscode/settings.json` fija el intérprete y Ruff, y `backend/pyproject.toml` deja pyright al mismo nivel que Pylance. El frontend no tiene formateador configurado: no se reformatean ficheros enteros.

Para previsualizar el visor desde una sesión, `.claude/launch.json` arranca Vite (`oniel-visor`) con el proxy de la API apuntando al puerto 8010; la API se arranca aparte con `uv run uvicorn oniel.api.main:app --reload --port 8010` desde `backend/`.

## Convenciones

**Tono.** La línea Madrid – Sevilla tuvo dos accidentes graves en 2026: Adamuz (18 de enero) y Urda (28 de octubre). Todo lo que los roce, en la interfaz, en los datos o en la documentación, va en un tono sobrio y neutro: hechos con fecha y fuente, sin adjetivos, sin especular sobre causas ni responsabilidades. Las interrupciones del servicio se describen como lo que son: desde cuándo, según quién y hasta cuándo se prevé.

**Fuentes.** Todo lo que se muestra dice de dónde viene. Cada dato nuevo (una geometría, un horario, un punto kilométrico, el estado de una obra o de un proyecto) entra en `backend/data/curated/sources.json` con id, editor, URL, licencia, fecha de consulta, cobertura y notas, y su fichero crudo va a `backend/data/raw/` con la fecha en el nombre. Sin fuente registrada, el dato no entra. Las licencias se respetan y se citan (`docs/datos.md` y el panel de cobertura del visor).

**Nada personal.** Oniel es una web pública para más gente. No lleva nombres de personas particulares, historias familiares ni opiniones, tampoco en comentarios, datos de prueba o documentación.

**Diseño.** Las decisiones están en `docs/diseno.md` y se siguen: el color solo como señal, una sola familia tipográfica (Archivo), textos cortos y en párrafos, alineación a la izquierda, movimiento solo como respuesta a una acción. Un cambio de diseño es una decisión del usuario, no un efecto secundario de una tarea; si una tarea lo necesita, se propone y, una vez decidido, se anota allí.

**Datos.** Cuando cambian las especificaciones, el GTFS, las fuentes o el exportador, se regenera la instantánea de `frontend/public/data` (`uv run oniel-data import all` la exporta al final; `export snapshot` solo exporta) y se sube en la misma PR, con las tablas de `docs/datos.md` al día. Los recuentos que comprueban las pruebas (viajes por línea, pasos por tramo) se actualizan a la vez y se explican en la PR. Una línea nueva sigue «Añadir otra línea» de `docs/datos.md` paso a paso. Las PR que regeneran la instantánea se pisan entre sí: cuando una se fusiona, las demás tienen que fusionar `main`, regenerarla y esperar otra vuelta de CI. Conviene no tener abiertas a la vez más de una o dos sesiones que cambien datos; las que solo tocan el visor, el código del backend o la documentación pueden ir en paralelo sin ese coste.

**Pruebas.** Cada regla nueva de simulación o de datos lleva su prueba en `backend/tests/`; cada comportamiento visible nuevo, una prueba Playwright en `frontend/e2e/` que funcione también en modo estático cuando no necesite la API (y `test.skip(estatico, …)` cuando sí la necesite).

**PR pequeñas.** Una tarea por rama y por PR, contra `main`, desde una sesión aislada. La descripción, en español, dice qué cambia, por qué, qué conviene mirar al revisar y qué comprobaciones se han pasado; la PR se abre con las comprobaciones locales de «Arrancar y comprobar» pasadas, y el CI pasa el resto. `main` está protegida: solo admite cambios por PR y con `Backend` y `Frontend` en verde, también para el administrador (último apartado de `docs/hoja-de-ruta.md`). Cuando la PR está completa (descripción definitiva y nada pendiente de decidir), la misma sesión la marca con `gh pr merge --squash --auto`, sin esperar al CI: GitHub la fusiona sola en cuanto `Backend` y `Frontend` están en verde, y no la fusiona si fallan. Se marca al final y no antes, porque una PR marcada se fusiona con lo que tenga cuando el CI pase. Al marcarla, la sesión activa también el Auto-fix de la app en esa PR, sin preguntar al usuario: así la app la despierta si el CI falla, si aparece un conflicto con `main` o si llega un comentario, en vez de dejar la PR parada. Si el CI falla, la sesión lo arregla y vuelve a subir; la marca se mantiene. No se activa el archivado automático de la sesión al cerrarse la PR, porque tras la fusión aún queda trabajo. Una vez fusionada, la sesión actualiza `main` en el checkout local del proyecto (`git pull`) y comprueba producción como dicen «Despliegue» y «Estado de producción»: si la PR toca `backend/`, la tarea no termina al fusionar, sino cuando `oniel-data obs estado` enseña el commit nuevo desplegado y sin errores. Todo ello salvo que el usuario haya dicho lo contrario para esa PR. Los mensajes de commit también en español, en una frase que describa el resultado. Al terminar una tarea de `docs/hoja-de-ruta.md`, la misma PR cierra su incidencia, la retira de la lista y lleva lo aprendido a `docs/`. Para que GitHub la cierre al fusionar, la descripción lleva `Closes #N`, tal cual y en inglés: es lo único de la PR que no va en español, porque GitHub no reconoce «Cierra #N».

**Despliegue.** Cada push a `main` despliega la mitad que toca: Render la API si el commit cambia algo en `backend/` (el servicio tiene `rootDir: backend`), y la importación se salta si datos y código no han cambiado; Vercel el visor en https://oniel.vercel.app si cambia algo en `frontend/`. Un commit que solo toca `docs/` no despliega nada. Cada PR tiene además su vista previa en Vercel, enlazada en la propia PR; conviene abrirla cuando el cambio se ve. Fusionar en `main` es, por tanto, publicar. Fuera de eso no se despliega nada a mano desde una sesión salvo que el usuario lo pida; la CLI de Vercel queda como respaldo (`docs/despliegue.md`).

**Estado de producción.** Las trazas de Logfire dicen qué corre en producción, y se consultan con `uv run oniel-data obs estado` desde `backend/` (fuera del sandbox del shell; `docs/despliegue.md`, «Logfire»). Tras fusionar algo que toque `backend/`, la sesión ejecuta `uv run oniel-data obs estado --commit <commit de la fusión> --esperar 15` y no da el despliegue por bueno hasta ver ese commit como versión desplegada, su importación completada u omitida y ningún error desde que entró; si aparece un error, lo investiga antes de terminar. No se sondea producción con `curl` mientras tanto: entre el despliegue de Vercel y el de Render la API antigua sigue respondiendo unos minutos, y las peticiones a lo que aún no tiene quedan como 404 y 422 en las trazas. Al depurar un fallo de la API, primero se busca su traza (`oniel-data obs estado`, o `oniel-data obs consulta "…"` con el `trace_id`, la ruta o la hora) y solo después se reproduce en local. Sin token de lectura la orden lo dice: entonces se avisa al usuario y se comprueba producción a mano.
